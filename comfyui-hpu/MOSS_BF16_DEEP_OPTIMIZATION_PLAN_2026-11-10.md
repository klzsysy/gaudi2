# MOSS BF16 深入优化计划

日期：2026-11-10。起始产品 `b1163be0`。用户要求先深入挖掘 BF16，积累可复用的执行优化经验，再考虑 INT8/FP8。本文是待执行计划，不代表新增性能结果；本轮没有修改产品或启动 HPU 实验。

## 目标与基线

继续保留当前 BF16 模型、1024²、25 步、CFG 2.5、er_sde/simple、原扩写能力和采样工作量。主线复用 Kitchen、PyTorch 和厂商已有算子；暂不自写 kernel，不以减步、缩短文本、换小模型或近似跳层实现目标。

| 度量 | 起始结果 | 第一门槛 | 深挖目标 |
|---|---:|---:|---:|
| 固定 caption 的 KSampler | 18.384 s，5 warm median | 配合缓存整图达标 | 根据真实算子上限确定，争取约 10 s |
| 文本缓存后的整图 | 18.764 s，单次使用验证 | **≤14 s**，补齐5 warm基线 | **10–12 s** |
| 完整重算、自然结束扩写图 | 29.673 s，5 warm median，298 tokens | **≤20 s** | 按各阶段实际预算继续推进 |
| TextGenerate | 9.162 s，5 warm median | 在固定轨迹验证下争取 **5–6 s** | 由小 M/状态/同步上限确定 |

这些是验收方向，不是收益承诺，各行不能直接相加。DiT 矩阵工作下界 5.78 s 不含非 GEMM 成本；当前 AIP≈61% 和有效矩阵峰值比例≈31.4% 是两种指标。AIP 向80%靠近仍保留，但以真实单请求延迟和有效工作效率判断，不靠增加批量/无效工作抬高占用率。

总体顺序为 **P0 归因 → P1/P2 按证据选择 DiT 主攻点 → P3 attention → P4 文本 → P5 条件触发的执行模式实验**。如果 P0 明确证明 attention 或 host gap 更重要，允许提前对应阶段。先给主要耗时分配实验资源，VAE/图片输出合计约0.25 s，暂排最后。

## P0：建立真实形状的性能预算

### 要回答的问题

18.38 s 中，多少是真实矩阵计算，多少是 attention 非矩阵运算、norm/SiTU/调制、布局与拷贝，多少是 CPU/运行时提交造成的设备空隙？在当前软件栈和精度约束下，真实算子最快能达到什么速度？

### 实验

1. 固定当前 caption、负提示词、latent seed、模型/代码哈希；正负条件307/23 tokens，对应主干 N=4403/4119，50次前向×42层。建立完整重算、关闭扩写但重算编码、文本缓存三组独立基线；cold、warm、带 profiler 的诊断分别报告。
2. 捕获代表层0/20/41、早/中/晚采样阶段以及两种条件的真实输入。用少量诊断请求收集 CPU/HPU 时间线、MME/TPC/DMA 活动区间、同步等待、编译/recipe命中、张量分配和布局转换。优先复用既有原始 trace + Perfetto；厂商高层摘要曾存在兼容问题，不依赖其总计。
3. 对四类真实 BF16 Linear 形状分别测：`[N,3072]×[3072,9216]`（QKV）、`[N,3072]×[3072,3072]`（输出）、`[N,3072]×[3072,16384]`（up/gate）、`[N,8192]×[8192,3072]`（down）。保持实际 stride、转置、累加/输出精度和权重布局；比较现有层调用、现有编译区和厂商现有矩阵入口。
4. 同时测真实 attention 形状 `[1,24,N,128]`，区分 QK、softmax、AV 及前后 norm/RoPE、布局、临时张量。核实底层实际融合/精度，不凭 Python 函数名字判断。
5. 单算子重放后再测真实 block、轮换42层权重的执行和完整25步。避免同一个小 block 热循环因权重复用、缓冲复用而夸大整图收益。记录实际工作频率、功耗及是否降频。

### 产出与分流

产出一张可核对的表：`区域 / 调用次数 / 关键路径时间 / 原生算子可达到的时间 / 候选可节省量 / 证据`。计算时间按时间线区间并集和依赖关系处理，不相加重叠 kernel、嵌套 host/device duration；未归因部分显式保留，目标解释约90%的关键路径。

- 主干 GEMM 明显低于同 shape 有效最优：优先 P1。
- 设备计算本身已快，但连续执行出现明显空隙/重复提交：优先 P2；若剩余 host gap 足够大，再触发 P5。
- attention 中间矩阵/softmax/布局占主要成本：提前 P3。

本轮首先交付这张性能预算表和一个收益最大的候选原型，不预先把“81%的矩阵 FLOPs 属于 Linear”解释成“81%的实际时间属于 Linear”。

## P1：让现有 BF16 矩阵路径达到真实形状的可用上限

重点检查 QKV/up-gate 已融合之后的剩余问题：输入和权重的 stride、隐式 contiguous/transpose/copy、重复 cast、层包装与 recipe 的开销。一次只改一个因素，分别验证对两个 N 的影响。

- 若现有 Linear 比相同输入布局的底层 GEMM 慢，定位差值是否来自参数 cast/offload、布局准备或编译包装；在已有 ops/加载机制所属层修复。
- 若底层 GEMM 自身随布局大幅波动，先测试现有合法布局和厂商路径；把一次性准备成本与每次执行成本分开。不要为当前 checkpoint 任意 padding，有 padding 候选时计入新增 FLOPs、掩码、位置语义和复制成本。
- 权重布局优化沿用既有参数/ModelPatcher 生命周期，验证 LoRA/补丁更新、卸载重载和不同 shape；不另建脱离生命周期的整模型权重缓存。
- 静态 recipe 已经启用；只在观察到编译失效、形状切换退化或命中问题后调整，避免重复测同一开关。

局部提升必须在真实 block 和固定 caption 的25步中兑现。用同 shape 的实测可用上限衡量效率，不要求每种形状都达到432 TFLOP/s。

## P2：减少点运算、提交和不必要的数据流转

现有编译区已经覆盖 attention 投影和 FFN。下一步按 trace 检查仍在区外的 modulation/RMSNorm、gate/residual、每层权重准备、hook 检查、临时分配及 Python 控制。

1. 对占比最高的短链先尝试现有 Kitchen 复合操作或局部编译。保持现有显式 dtype、舍入和原地/别名语义，并检查是否减少设备 kernel、临时内存和关键路径时间。
2. 仅在证明不变量稳定且不会漏掉动态 hooks/patches 时，将重复准备移到其所属调用的外层；保留原兼容分支，不绕过 cast/offload/hook 合同。
3. 若仍存在足够多的区域边界开销，再尝试单 block、更小数量的连续 block（例如2层，再4层）执行区域；先保留已知敏感的调制/残差边界，观察 graph break 和编译成本。一次扩展未带来净收益就停止扩大，避免整模型编译成为独立工程。
4. 临时缓冲只在本次执行内复用；检验改写是否增加峰值或延长大 tensor 生命周期。不能以固定地址为由把跨请求 tensor 缓存挂到模型上。

已有 FP64 对照显示部分编译残差比原执行更接近高精度参考，故“图片不逐像素相同”不自动等于质量退化；但也不能以此忽略累积误差。扩大融合必须通过 P6 的数值和完整质量门槛。

## P3：在相同精度要求下优化 BF16 attention

已有结论必须作为本阶段起点：厂商默认 FusedSDPA 未胜过当前编译路径；fast softmax 较快但局部 FP64 参考误差明显增大；FP32 softmax 更慢。没有新原因时不重复同一组模式测试。

本轮只对 P0 发现的具体费用做实验：

- 检查当前 backend 是否实际物化巨大 N×N 中间张量，是否存在可去除的 cast、transpose 或 copy。
- 对现有公开 BF16 attention 操作，连同真实输入布局、mask 和前后 norm/RoPE 一起比较，计入全部适配成本。
- 若需评估分块/在线 softmax，先确认已有实现支持当前精度和数学语义；分块结果必须按正确归一化/LSE 合并，不能平均各块输出。无现成有效路径则记录限制，不进入自写 kernel。
- 只有解决具体精度问题或证明原误差判断过于局部后，才重新考虑曾失败的模式；不为速度放宽默认数值门槛。

先用真实多层、多 timestep、正负条件输入证明数值和局部净收益，再做整图；避免将单首层的毫秒数乘2100当成已经实现的节省。

## P4：把文本扩写和正负编码一起纳入 BF16 深挖

DiT 达到第一门槛后，完整图仍需缩短约10.9 s的扩写/编码工作；同时 P0 可以先收集文本阶段证据。文本实验使用固定1970-token输入和既有298-token轨迹，另保留自然结束生成。

优先顺序：

1. **Prefill/编码**：目前 MLP 和完整 attention 的新增编译重点是≤8-token decode。对1970、307、23等真实长度，测 Linear/MLP、prefill attention 和 GDN 分区编译及布局准备；不要直接把 decode 执行方式套给 prefill。
2. **Decode 调度/同步**：测 `.item()`/CPU回读、采样、mask/索引准备和 host 提交间隙；减少可证明冗余的同步和重复准备，保持采样 tie policy、随机数和停止条件。
3. **MTP/GDN 状态**：用固定验证树/接受路径重放，检查状态复制、rollback、卷积与GDN更新是否仍有冗余。保留已修复的同 storage 行搬移语义，不能为了少一次 clone 重新引入静默错误。
4. **MTP 形状与有效 KV**：现有8-token联合attention和连续KV已存在；有效前缀裁剪之前没有稳定端到端收益。只有新 trace 证明瓶颈发生变化，才重试分桶/树形状方案；记录验证轮次、草稿数、接受token数和内存流量，不能单看输出token/s。

通过固定轨迹性能/数值检查后，再用多提示词自然结束生成检查是否真实受益。Teacher forcing 若使用 MTP off，只能评价该路径；MTP收益需补固定树或匹配调用轨迹，不能据不同长度输出宣称严格提速。

跨请求前缀缓存不计入本轮完整重算成绩，保留为独立场景。文本5–6 s为预算目标，不是对现有9.16 s已找到确定的3–4 s收益。

## P5：以证据触发执行模式实验

本机已安装 Habana 1.24.2 的 HPUGraph 要求 lazy，而产品依赖 eager + torch.compile。把 HPU Graph 当作后备的独立实验，不当成随手可打开的优化。

触发条件：P1–P3 后仍有明确的 host/提交空隙，例如占采样关键路径约10%以上，且预期可消除费用足以覆盖模式切换成本。

实验先用隔离进程和真实单 block/两种条件形状，逐级验证 lazy/graph 的算子支持、动态 timestep、输入地址、状态/别名与精度，然后才进入完整DiT。单请求内捕获/预热费用必须计入该请求，不能假设跨请求持久图缓存免费；单列cold/warm、编译时间、额外显存与卸载行为。

只有完整25步净收益和生命周期都通过才讨论产品接入。若厂商模式要求与产品状态所有权冲突，记录为本栈限制；不能通过整体切换日常服务来试错。

## P6：每轮验收和可复用产物

### 性能

- 普通候选先短重放筛选，再基线/候选各1 cold+至少5 warm；稳定计时不插入逐算子 synchronize，不加会改变编译分流的 module hooks。
- 记录中位数、范围、峰值内存、fallback、cold成本和关键路径；收益必须明显超过基线波动。≤3%的候选需二次交错对照，只为低复杂度且重复成立的收益投入维护。
- 固定 caption 的DiT、固定轨迹的文本、自然结束完整图分别报告。缓存命中不是完整重算的提速，局部重放不是完整workflow收益。

### 正确性和兼容性

- 局部真实输入与CPU高精度参考比较，覆盖早/中/晚步骤和浅/中/深层；检查高精度误差是否系统性恶化，而非单纯要求像素相等。
- 完整质量集合覆盖原街景、文字海报、人物、复杂构图、短/长和加权提示词，固定成对seed并比较基线自身波动；文字/主体/结构退化单独记录，不以finite替代质量。
- 512/768/1024、形状切换后回到原尺寸、hooks/patches、禁用编译、模型卸载重载；触碰公共ops时补对应CPU和其它受影响路径的可用回归。
- 原INT8文本模型兼容性作为回归保留，但不计入BF16性能收益。完成后校对服务器文件哈希，恢复日常服务并重放原工作流。

### 为后续精度路线留下什么

1. 按真实shape的矩阵/attention性能表，以及包含布局与准备成本的可用上限。
2. 可复用的真实输入重放、高精度参考和完整质量样本。
3. 经过验证的区域边界、状态/缓冲生命周期、编译失效和hook处理方法。
4. 匹配工作量的文本/MTP与整图验收工具，以及所有未成功路线的原因。

这些工具先用于BF16，未来可以在相同输入、数值和计时合同下替换矩阵精度，减少重复调查。

## “BF16 已充分挖掘”的判据

不以某一个AIP数字宣布完成，也不因两次失败直接判定硬件上限。应同时具备：

- 主要时间已归因；高占比GEMM接近同shape、同精度的实测可用上限，例如达到其70–80%以上，剩余差值有解释。
- host gap、额外拷贝、重复计算和可用公开融合操作都经过验证，主要未采纳路径有性能或正确性证据。
- 两轮针对不同剩余热点的优化后，继续改善的端到端收益已接近噪声或小于约3%，或者剩余成本明确落在当前厂商算子能力边界。
- 固定工作量的出图/完整图已达到目标，或尚未达到但具备足够证据说明差距所在；保留明确的潜在收益清单。

达到这些条件后再讨论下一条路线。当前尚处P0之前，不能把18.38 s视作BF16已经接近极限。
