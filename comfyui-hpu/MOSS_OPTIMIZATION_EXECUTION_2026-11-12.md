## GDN专用核心

本轮保留FP32状态、既有投影、卷积、门控、归一化及deferred buffer协议，将上轮已接受行的状态提交与当前树形输出放入一个TPC算子。程序仍携带行号及commit位，设备端读取pending数，跳过填充行。输出状态归调用方所有，每次调用产生输出张量，后续写回现有状态。

### 核心迭代

| 实现 | 32头、8行核心耗时 |
|---|---:|
| 当前编译基线 | 约0.182–0.188ms |
| 首版逐列、global scalar读取 | 约0.88ms |
| vector广播替代逐次scalar读取 | 约0.34ms |
| 共享Q／K及gate读取 | 约0.254ms |
| 共享读取并仅提交3个有效行 | 约0.207ms |
| 四列并行，仅提交3个有效行 | 约0.084ms |
| 四列并行，pending为0 | 约0.075ms |

四列版本同时复用Q／K、gate和value读取，并为归约提供更多独立工作。固定298-token程序的130次控制中，pending为0／1／2／3的次数分别为2／16／57／55。低head数原型的收益未用于推算32头的收益。

最终核心合成检查覆盖batch1／2、heads2／32、rows1／4／8、链形／分叉／重排行序及pending0／3／8。FP32状态与输出相对误差约10⁻⁷量级。50项GDN相关测试通过，完整产品回归为287项通过。

本轮调查脚本、性能记录和服务器路径集中保存在本仓库。产品源码只包含实现与便携构建入口。产品路径287项回归通过，三组自然图片、512²卸载重载／MTP off及原INT8文本运行成功，fallback为空。allocator峰值约31.277→31.286GiB，增加约9.6MiB，卸载回到2,685,928,832 bytes。

## 失败路径与运行条件

- C++扩展最初链接lazy插件导致重复注册，改为当前eager进程所用的`libhabana_pytorch2_plugin.so`。算子采用HPU dispatch、`hpu_custom_op_pt2.h`和`custom_op`命名空间，并注册fake metadata。
- 最初缺少shape inference导致图创建失败，补齐后独立编译与完整graph执行通过。
- SiTU原型的BF16／FP32转换曾混用lane布局，修正为匹配的默认转换后恢复正常误差。输入转换使用`SW_LINEAR`的尝试触发TPC编译器错误。
- 当前工具链对这些kernel只提供16KiB VLM。32KiB缓存、20KiB GDN缓存及占满16KiB后发生spill的版本均构建失败。SiTU缓存60个BF16向量并重算末512列，GDN缓存Q／K、复用gate向量后构建通过。该限制来自本轮编译器报错，设备总VLM与各编译模式需区分。[厂商TPC架构说明](https://docs.habana.ai/en/latest/TPC/TPC_User_Guide/Processor_Architectural_Overview.html)
- 首次完整流程launcher覆盖了外部`GC_KERNEL_PATH`，自定义GUID创建报synStatus26。已在调查launcher保留传入库路径，重试完整流程通过。
- logits保存使对应warm增加约2秒，相关样本已排除出计时统计。

驱动、固件、内核和设备功耗配置沿用第10节测量环境。本轮GDN收益来自算子内数据复用、SIMD调度及提交合并。

## 对投入顺序的修正

1. GDN四列核心曾取得局部及整段收益，因完整质量变化已撤回。源码和二进制哈希保留为候选历史证据。
2. Attention后续投入聚焦QK分数的SRAM驻留和MME／TPC联合调度。本轮Python query分块增加整层成本，下一实现需验证编译后存储位置与整层耗时。
3. SiTU约1.01秒的预算中，若实现2倍速度，理想节省约0.505秒。现有原生原型尚未达到当前编译结果，后续需要改变融合边界或特殊函数／访存实现。
4. 量化独占约0.20秒，完全消除的理想收益也受此预算限制。norm／调制／量化联合融合需按共享访存重新测量。
5. 当前BF16 QK约2.406秒、softmax约1.340秒，合计约3.746秒。若二者互斥预算减少35%，对应约1.31秒DiT节省。该情景的剩余空间大于本轮GDN整段收益，但实现难度涉及编译器和片上存储调度。
